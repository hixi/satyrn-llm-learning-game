# Wave 0 — The Frame: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the reusable frame of the Satyrn learning game — app shell, hash router, persisted store, typed content graph with a build-time link checker, companions, dialogue, achievements, and the Prologue (Lantern Room) Bead end-to-end — deployable to GitHub Pages.

**Architecture:** A static Vite + Lit application. Game structure lives in typed TS manifests and prose in YAML/Markdown under `content/`; a Node build step validates and link-checks it and writes a generated bundle the app imports. A small event-bus store persists to `localStorage` with versioned migrations. Each Bead's puzzle is a Lit custom element behind a documented mechanic contract with a mandatory accessible path. Hash routing keeps GitHub Pages deploy trivial.

**Tech Stack:** TypeScript, Vite, Lit 3, Vitest (+ jsdom), Playwright, Zod, `yaml`, `tsx` (Node TS runner), npm.

**Spec:** `docs/superpowers/specs/2026-10-02-satyrn-book-as-game-design.md`

## Global Constraints

- Browser-only. No backend, no accounts, no runtime network calls.
- Deployed to GitHub Pages; hash routing; Vite `base: './'`; no server rewrites.
- No reuse of the purchased Triple Charm webfonts or other licensed `satyrn-zen` assets. Art and identity are original. Brand palette may be reused: yellow `#e3d678`, greige `#efe4d2`, charcoal `#383330`.
- Every part ID is namespaced and stable: `world.*`, `mechanic.*`, `character.*`, `concept.*`, `achievement.*`, `dialogue.*`, `thread.*`, `strings.*`.
- References are one-directional: world → concept/character/mechanic; achievement → world/mechanic; concept → concept (`related` only). No reverse references.
- Dangling references: local dev warns and the game shows a visible placeholder; build/deploy hard-fails. `--allow-dangling` is never passed by the deploy workflow.
- Lit + Vite. Mechanics own their styles (shadow DOM) and import nothing from another mechanic.
- Every mechanic declares an accessible path: keyboard operation, reduced-motion behaviour, a screen-reader description, and a "continue without playing" control.
- Achievements are data, evaluated over a fixed event vocabulary. Exotic predicates use the same documented seam used for testing — one seam, not two.
- State is versioned with migrations; the journal offers export, import, and reset.
- Node >= 22.6, npm. Unit tests run with jsdom; no test requires the network.
- A smoke e2e walks the Thread and enters each Bead.

## Review Focus

Inputs or conditions the spec implies but its prose does not test. Each has a test pinned in the owning task.

1. **Corrupt or absent `localStorage` value** (hand-edited or written by an older release). Expected: the game loads, migrating or resetting gracefully; never throws. (Task 7)
2. **Missing or empty `content/` at build time.** Expected: the build fails with a clear message naming the empty/missing directory; it never ships an empty game. (Task 5)
3. **A world references a mechanic id that is valid in content but has no registered element.** Expected: the world renders an accessible "mechanic not installed" placeholder instead of throwing. (Tasks 10, 13)
4. **Keyboard-only / reduced-motion completion of a canvas-capable mechanic.** Expected: the player reaches completion with no pointer input. (Task 14)
5. **Unknown hash route or an unknown world/concept id.** Expected: a not-found view; never a blank screen or an exception. (Tasks 9, 10)

- [ ] **Step 3: Implement `tools/content/schema.ts`**

Define the schemas exactly as the tests and the spec require:

- ID pattern helper: `const id = (ns: string) => z.string().regex(new RegExp('^' + ns + '\\.[a-z0-9-]+$'))`.
- `Condition` is a recursive discriminated union: leaf events `{ event: 'mechanic.completed'; mechanic?: string; world?: string }`, `{ event: 'world.entered'; world?: string }`, `{ event: 'world.skipped'; world?: string }`, `{ event: 'world.engineRoom.completed'; world?: string }`, `{ event: 'evidence.submitted'; mechanic?: string }`, plus combinators `{ all: Condition[] }`, `{ any: Condition[] }`, `{ not: Condition }`. - `WorldSchema = { id: world-id; title; act: 'prologue'|'act1'|'act2'|'act3'; order: int; keeper?: string; concepts: string[] = []; mechanic: string; summary; intro; engineRoom? }`.
- `AchievementSchema = { id; title; description; kind: 'lesson'|'skip'|'depth'|'journey'; condition?: Condition; predicate?: string }`, refined so exactly one of `condition`/`predicate` is present. A `predicate` names an exotic condition registered in code (Task 8); data over code is the default.

- `RawContent = { concepts; characters; worlds; mechanics; achievements; dialogues; threads; strings }`, each `Record<string, unknown>`.
- `DanglingRef = { from: string; field: string; target: string }`; `LinkDiagnostics = { dangling: DanglingRef[] }`.
- `Content` is the validated record-of-records. Export `z.infer` types for every schema.
